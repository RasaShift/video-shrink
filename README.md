# video-shrink

把码率过剩的视频重压成 AV1（或 HEVC），用 **30%–55% 的体积**换视觉上难以分辨的画质。

一个开箱可用的判断流程 + 批量脚本：先探硬件、再抽 120 秒定档、跑 VMAF 质检确认没有压坏，最后批量执行。

## 能省多少

本机实测（i5-12600KF + RX 7900 XTX，FFmpeg 9.0.2，硬编）：

| 源 | 时长 | 原片 | 成品 | 压缩到 | VMAF |
|---|---|---|---|---|---|
| 1080p h264 9.0 Mbps | 185 分 | 12.81 GB | 5.93 GB | 46.3% | 过线 |
| 4K60 h264 51.7 Mbps | 23.6 分 | 9.19 GB | 3.58 GB | 39.0% | 96.8–99.8 |
| 2.5K h264 36.1 Mbps | 2.3 分 | 0.62 GB | 0.19 GB | 31.0% | 98.3–99.0 |

**反例，请务必一起看**：

| 源 | 时长 | 原片 | 成品 | 压缩到 |
|---|---|---|---|---|
| 1080p h264 6.3 Mbps | 11 分 | 0.52 GB | 0.48 GB | **91.9%（只省 8%）** |

不是所有 1080p 都有得省。**码率是决定性因素**——码率越高、冗余越大，压得越狠；低码率或短片段可能几乎压不动。

## 什么时候别用

- **源已经是 HEVC 或 AV1**：二次压缩画质会掉线。实测 HEVC 源再压 VMAF 只有 93.71，跌破及格线，且体积只省 37%
- **1080p 源低于 4 Mbps**：冗余本来就少，压完更糊
- **还要剪辑、调色、做字幕**：先加工完再压
- **没有较新的显卡**：软编慢到不可行（实测 1080p 约 0.4x，一部 3 小时片要 7 小时以上）

## 硬件要求

AV1 硬件编码是 2022 年底才铺开的，**能解码 ≠ 能编码**：

| 厂商 | 有 AV1 编码 | 只有解码（常见误区） |
|---|---|---|
| NVIDIA | RTX 40 系及以上 | **RTX 30 系** |
| AMD | RX 7000 系及以上 | **RX 6000 系** |
| Intel | Arc A/B 系独显 | 多数核显 |

没有 AV1 编码可以退到 **HEVC 硬编**，损失几乎没有：同一源的 120 秒样本，AV1 qp35 是 56.6 MB / VMAF 96.20，HEVC qp20 是 58.9 MB / 95.99——体积只大 4%，分数只低 0.2，而且 HEVC 的播放兼容性远好于 AV1（约 95% 设备 vs 60–70%）。

## 用法

### 前置

| 工具 | 说明 |
|---|---|
| FFmpeg | Windows 用 [gyan.dev](https://www.gyan.dev/ffmpeg/builds/) 的 `essentials` 构建就够（含 AV1/HEVC 硬编）；要软编 SVT-AV1 需 [BtbN 全量构建](https://github.com/BtbN/FFmpeg-Builds/releases) |
| Python 3.8+ | 跑批量脚本 |

验证：`ffmpeg -encoders` 里能找到 `av1_amf` / `av1_nvenc` / `av1_qsv` 之一。

### 直接用脚本

```bash
# 先空跑一遍，看分档决策对不对（不压制）
python scripts/wb-encode.py "视频1.mp4" "视频2.mp4" --dry-run

# 正式跑
python scripts/wb-encode.py "视频1.mp4" "视频2.mp4" "视频3.mp4" --log run-log.tsv
```

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只探源和出决策，不压制 |
| `--vmaf-sample` | 抽样复检（首批仍全检，之后每 5 抽 1，体积比异常强制补检） |
| `--log <tsv>` | 每部结果带时间戳追加，便于记账 |

换机器 / 换显卡时，改脚本顶部 4 个常量（`FFMPEG`、`FFPROBE`、`VMAF_ARCHIVE`、`N_THREADS`），并把编码器换成对应厂商（`av1_nvenc` / `av1_qsv`）。

### 装成 AI 技能

本仓库同时是 WorkBuddy / Claude 技能格式：把整个目录放进 `~/.workbuddy/skills/`（或项目的 `.workbuddy/skills/`），`SKILL.md` 会被自动识别，之后说「硬盘满了想压片」就会触发。

## 方法要点

- **先抽样再批量**：从第 10 分钟抽 120 秒，试压后算 VMAF，分数 ≥95 才算「视觉难辨」。换分辨率或换码率级别（±2 Mbps）必须重测
- **一档一味**：1080p 5–10 Mbps 用 qp35，4K/2.5K 高码率用 qp45，都配 `-quality speed`（比 quality 档快 2.3–3.2 倍，画质分毫不变）
- **4K 的 VMAF 要用 4K 模型**：`model=version=vmaf_4k_v0.6.1:n_subsample=3`，且只看均值——抽帧后最低帧不可信
- **逐部压完即验**：中间有结论、掉线立刻停、不白花后续几部的电
- **原片只读**：删原片只在验收通过后由你自己决定

## 数据的局限

- 所有参数都来自上述单机实测，**换个片源、换个码率级就要重测**，不能照抄
- VMAF ≥95 是「视觉上难辨」，**不是无损**，不可逆
- 测速与压缩比受 GPU、驱动、FFmpeg 版本影响
